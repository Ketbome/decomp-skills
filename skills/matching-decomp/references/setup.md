# Starting a project

Goal of day one: the original binary rebuilt byte-identically from split assembly, the compiler identified by a byte
match of a few real functions, and the per-function check working. Everything else builds on that.

## 1. Legal and repository hygiene

- The repository contains no game data: the disc image, extracted files and generated assembly are ignored; the build
  checks the user's own copy against a known hash.
- Clean room: no leaked or copyrighted source code as reference. Decide this on day one and write it in the README.
- Pick a licence for your own work (CC0 or MIT are common) and state that it does not cover the game.

## 2. Split and rebuild

- Extract the executable; verify its hash. Make a flat image of what the loader maps (`objcopy -O binary`), and
  compare against that image, not the ELF.
- Use [splat](https://github.com/ethteck/splat) (`splat create_config`, then fix the segment table by hand from the
  ELF section headers: offsets are image offsets, and every gap between sections must belong to some subsegment).
- Build with ninja: assemble everything, link with the generated linker script, objcopy, compare. Alignment of
  sections that the linker script does not reproduce (e.g. `.sbss` on 128 bytes) is a frequent first mismatch.
- **Milestone: byte-identical rebuild from assembly only.** Commit and push.

## 3. Map the binary

- Strings referenced by functions, library version strings, source paths, and the call graph (libraries never call
  game code except allocators/callbacks) give the game/library boundaries. Measure progress on game code only.
- Look for tables of `{name, function}` pairs (script command tables, RPC tables): free real names.
- Look for checksummed names (many engines hash identifiers): build a dictionary from the game's own data and
  strings, then annotate constants.

## 4. Identify the compiler

- Clues: compiler version strings, debugger strings, section names, C++ mangling, prologue shapes, tail calls,
  constructors returning `this`, how callee-saved registers are saved.
- Collect candidate builds (the [decomp.me compilers](https://github.com/decompme/compilers) set covers most
  consoles; Windows binaries run on macOS/Linux with [wibo](https://github.com/decompals/wibo)).
- Write 3-5 small real functions in C and compile them with every candidate; keep the one that matches byte for
  byte. Then confirm flags (`-O`, `-G`, ...) with functions that exercise them.
- Record evidence in `docs/toolchain.md`.

## 5. Make C possible everywhere

- Convert the code area into C/C++ files ("chunks") with one `INCLUDE_ASM` per function, generated by splat
  (`c`/`cpp` subsegments). Fixed-size chunks at function starts are fine to begin with; real object boundaries can
  come later.
- Compile flow: compiler → (assembler filter) → modern assembler with a prelude → object. Keep the per-function asm
  for every function, matched or not (splat `disassemble_all`), so checks always have the original.
- Make the configure step self-healing: re-add `INCLUDE_ASM` lines splat knows but a source lacks.
- Install the check tool: copy `scripts/dk.py` and fill in `decomp.toml` (templates/). Verify with a function you
  already matched: `dk check`.

## 6. Prepare for parallel work and interruptions

- `docs/decomp_guide.md` (project rules: linkage, data, globals, flags), `docs/agent_protocol.md` (from
  templates/), `docs/STATE.md`, `docs/worklog/`.
- A one-command integration script: `dk docs --commit`, build HEAD in a separate worktree, push if identical.
- `AGENTS.md` (template in templates/; Claude Code, Codex, OpenCode, Cursor and Copilot read it) with the session
  start, roles, stack, commands, layout, conventions and the clean-room rule. One file: a second instructions file
  (e.g. a `CLAUDE.md` copy) drifts. Claude Code reads `AGENTS.md` only when no `CLAUDE.md` exists.
- The progress table of the README between `<!-- dk:progress -->` markers, filled by `dk docs` (`[docs]` in
  decomp.toml): numbers typed by hand go stale.
- Claude Code: the SessionStart hook of templates/claude-settings.json in `.claude/settings.json`, so every
  session, `/clear` and compaction starts from `dk state`.
